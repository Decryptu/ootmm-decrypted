# Disposable gameplay tests

`tools/gameplay_test.py` runs BizHawk 2.11.1 from the command line with a new output directory, a copied ROM and Lua connector, and separate configuration and save paths. It never reuses an output directory. Load only a checkpoint made with that exact ROM and seed. Matching unpatched payloads do not establish savestate compatibility after repacking: loaded DMA tables and object/overlay state can still refer to the previous ROM layout. Create a fresh file or use a matching native save when rebuilding a ROM. For a native-save recovery test, use `--save-ram <file>` instead of `--state`: the runner copies that file, preserving its basename, into the isolated `N64/SaveRAM` directory and starts the ROM without loading a savestate. Use the SaveRAM produced by the matching ROM and verify the game's own save confirmation before closing it. Keep ROMs, checkpoints and evidence under ignored `dist/`.

Supply `--emulator`, `--config`, `--connector` (Archipelago's `data/lua/connector_bizhawk_generic.lua`), `--rom`, one of `--state`, `--save-ram` or `--fresh-boot` (a menu-input scenario creates a new file), `--seed` (the `.archipelago` file), `--placements` (the slot's `.ootxmm.json`), `--slot`, `--scenario` and `--out`. `--timeout` bounds wall-clock seconds, including startup. The emulator window stays hidden. Use `--setup-note` repeatedly to describe modifications inherited from earlier checkpoints.

For a real pickup assertion, also supply `--ap-python` (the Archipelago environment's Python), `--archipelago` (its source checkout) and `--expect-check "OOT Mido's House Top Left"`; repeat `--expect-check` for several checks. `--min-game-switches N` additionally requires N changes between live mailbox addresses; the observer records discovery and reconnects the connector socket when necessary. Stage the current world in that checkout first with `python tools/build_apworld.py --dir dist/ap-test/worlds/ootxmm`. The observer starts a disposable loopback server, attaches slot 1 to the real connector and waits for the named checks from the game. Startup waits up to 30 seconds for the N64 ROM domain after the Lua socket appears; the runner passes the input ROM's SHA-1 and the observer rejects a different ROM before gameplay assertions. Reports record the verified connector hash. It verifies each expected check queues exactly one matching item for its recipient. It does not inject checks unless `--inject-remote-count` is explicitly supplied. This mode currently tests slot 1 only; the original remote-delivery mode of `emulator-smoke.py` still simulates slot 2's pickups.

For a boss assertion, supply `--expect-boss MM_MAJORA` or `--expect-boss OOT_GANON` with the same Archipelago arguments; repeat it for both. The observer injects no awards in this mode. It requires the real client to confirm each boss in server storage, then checks that the server completion status agrees with the configured goal. Reports include stored boss progress and completion status. Observer failures also write a failed report with the error, observed checks, stored goals, receipt index and mailbox history before cleanup; a timeout must never be treated as victory evidence.

Diagnostic `--grant-item "<AP item name>"` supplies an explicit temporary-server item grant and requires `--expect-received-index`; reports list these separately as `setup_grants`. This can prepare inventory through the real item handler, but does not verify a source pickup. Add `--grant-after-capture paused` to delay those grants until the scenario creates its `paused` screenshot; the capture must exist in the scenario. Polling continues while waiting, bounded by the observer timeout. Put a native-state assertion before that capture and retain another assertion and capture before resuming. The manifest records the capture name; `grant_barrier` records the queue timestamp and receipt index. Compare its Unix timestamp with the capture file timestamps to establish that awards queued during the asserted state. The standalone observer also accepts `--grant-ready-file <marker>`; use a new marker in a disposable directory.

A restored boss flag alone does not prove a new victory; begin victory tests with a fresh server and retain the fight evidence. Continuous native completion, the opposite boss order and other goal settings remain release gates.

The standalone server observer timestamps `mailbox_history` entries with monotonic `elapsed_seconds`. Its `mailbox_timing` report records the longest client poll, each observed mailbox-loss-to-rediscovery interval (including reattachment at the same address), and the duration of an unfinished recovery on failure. These intervals include loading and discovery delay; they do not measure the black screen or establish that a native transition occurred. Use the matching scenario's actual transition and active-payload assertions, plus screenshots, to interpret them. Compare identical ROMs, checkpoints and emulator configurations when assessing game-switch scan overhead.

Both server observers include `mailbox_load`: read-only header snapshots before and after client polls, valid/invalid sample counts, disconnected samples, last ring occupancy and high-water marks for each 2 KB ring (2047 usable bytes). Two-player evidence is under each final observation. Modulo arithmetic handles wrapped offsets; stale magic and out-of-range offsets are counted as invalid instead of interpreted as load. These sampled maxima can miss peaks between reads and do not measure packet latency or establish that a pause or fast-forward occurred. Pair them with scenario events and receipt stability assertions.

For rapid real-source tests, bracket each controller interaction with named captures and compare their event timestamps. Require every source as an `--expect-check`, compare `new_checks` with the exact expected set, and retain the per-source single-award assertion. Separate local native inventory assertions from awards queued for an absent remote slot. Saved scene flags need not reflect live chest state until the game saves or leaves the scene; do not use them as immediate interaction assertions. The candidate's three-chest test starts interactions 2.66 seconds apart at requested 400% speed; native dialogue bounds that cadence. Its frozen evidence is `dist/native-recovery/rapid-02`, with hashes and assertion results in `dist/native-recovery/RAPID_VALIDATION.json`.

Connector request failures during these snapshots follow the observers' normal reconnect path, including a timeout while the core loads the other game. They must not terminate observation or count as a successful poll. Final source, receipt and stability assertions still have to pass within the run's timeout.

For native pause assertions on v33.0, read the two-byte `PauseContext.state` through the active game's `gPlay`: OoT's offset is `0x10760 + 0x1d4`, MM's is `0x16d30 + 0x1ec`. State `6` is the main menu and `0` is closed. Verify layouts against the matching `combo/oot/play.h`, `combo/oot/pause.h`, `combo/mm/play.h` and `combo/mm/pause_menu.h`; do not reuse one game's offset in the other. MM's native inventory starts at `MmSave + 0x70`; use the `ITS_MM_*` slots and `ITEM_MM_*` values in `combo/data/items.h`. Capture inventory before grants as well as while paused: queueing during pause alone does not establish that native item application waits for resume.

Use `--save-server` to write `server.apsave` into the new output directory after the server assertions pass. A subsequent run can restore it with `--server-save-input <file>`; the server checks its multiworld identity. Inputs are never overwritten. Reports distinguish restored checks from newly reported checks; a restored check alone is not evidence of a new pickup.

`--expect-received-index N` additionally waits for the game's WAL query index to equal N and requires that same index on each of 16 further polls (`stable_polls` in the report). For a controlled delivery stimulus, `--inject-remote-count N` simulates N previously unchecked slot 2 locations that award slot 1 items; it requires an expected index. When combined with `--disconnect-seconds`, these awards are queued while the recipient is disconnected. The observer verifies that the disconnected client receives nothing before reconnecting, then waits for the requested game index and stability polls. Reports record the queued count and label these simulated checks. This tests actual recipient handling and recovery, while the source pickups remain protocol simulation. Omit this flag when observing real pickups.

The output includes input hashes, slot settings and setup notes in `manifest.json`, the exact scenario, frame- and wall-time-stamped `events.jsonl`, screenshots and states at capture steps, emulator logs and `result.json`. Lua event `elapsed_seconds` starts when the scenario loads; observer elapsed times start in the observer process, so compare intervals within one log, not timestamps across the two processes. A wall-clock timeout writes a failed result with the last logged event when available, even if the core stopped advancing frames; cleanup terminates only the runner's own processes. Pickup runs also include `server.txt` and `server-result.json`, with observed checks and their item recipients. The runner succeeds only if both the scenario and requested server assertions pass. A completed input sequence alone proves no pickup or victory. Received-item index and server reporting do not prove player 2 used the item in gameplay.

`--interrupt-pickup before-send` aborts the actual WebSocket transport inside the first expected check's send call, after the client retains the check but before delivery. `--interrupt-pickup after-accept` sends normally, waits for the disposable server to accept that check, then aborts before the call returns to the game watcher. Both require new real pickup assertions and exclude other disconnection modes, grants, boss assertions and simulated checks. Normal client polling clears the game's connected flag, then normal login resends retained checks. Reports require the interruption to occur, record server acceptance at abort, and verify exactly one award, no extra checks and 16 stable recovery polls. Supply `--expect-received-index` to assert the index on every stability poll. Use a scenario that performs the actual pickup and checks its native inventory effect. Expected abrupt-close errors in the socket log are evidence of the fault, not a passing result by themselves. These tests cover the two acceptance outcomes at controlled send boundaries; they do not simulate arbitrary byte-level fragmentation or a client-process crash.

`--disconnect-seconds N` disconnects the temporary server client after the first game query, clears the game's connected flag through the normal client, polls offline for N seconds (at most 60), and reconnects. The observer asserts that no new checks reached the server during the interruption, then requires the expected checks and exactly one award each. Pair this with scenario assertions for initial attachment, disconnection, the actual inventory change while still disconnected, and reattachment. For multiple offline interactions, assert disconnection before and after the second input and require both exact checks after reconnect. OoTMM v33.0's `Multi_EnsureSendBufferEmpty` waits for the pending acknowledgement before a second reliable send; recovery after reconnect does not establish unrestricted offline play. No source packets or check flags are injected.

For pending-check persistence across a native save, use `--save-offline` instead of `--disconnect-seconds`. It requires expected pickup checks absent from the restored server and excludes simulated checks, grants and boss assertions. After the first live query it disconnects through the real client, verifies the game's connected flag is cleared, and stays offline until the scenario finishes. Use `wait_client`, then assert disconnection, perform the real pickup, assert its native inventory effect and disconnection, and save through the game's menu. The runner requires a nonempty native SaveRAM output; inspect the captured native save confirmation as well. The observer asserts that the server gained no checks or client deliveries. Its `offline-save` report lists pending checks to verify later, without claiming they were reported.

Pair that phase with a separate `--save-ram` cold boot and `--server-save-input` from the offline phase, using `--save-server` to retain its server state. Require the same `--expect-check` names, saved native inventory/check flags and the retained `--expect-received-index`. The cold-boot report must list each pending check under `new_checks` and verify exactly one award. Restored checks or a successful offline phase alone do not prove recovery. The candidate covers one real own-item chest pending across this restart, alongside two retained remote receipts from the two-player round trip. Separate real-chest runs cover both socket send boundaries; unrestricted offline play remains unestablished.

## Two running players

Run `tools/two_player_gameplay.py --archipelago <checkout> --plan <plan.json> --out <new directory>` with Archipelago's Python. Stage the current world first. The coordinator starts two hidden isolated scenario runners, two real game clients and one temporary server. It verifies each connector's ROM SHA-1 before attaching, observes real source checks in both slots, verifies exactly one matching award per expected check and waits for both games' requested received indices to remain stable for 16 polls. Both Lua scenarios must also pass; use read-only inventory assertions to establish the received item's effect. No source checks or awards are injected. The report includes the disposable server save and separate evidence directories for both games.

The JSON plan has `seed`, `emulator`, `config`, `connector` and a `players` array with slots 1 and 2. Each player supplies `slot`, `rom`, `placements`, `scenario`, `checks` (exact location names), `received_index` (positive), and one of `state`, `save_ram` or `fresh_boot: true`. Paths resolve from the working directory. Each slot must have an expected source check awarding the other player. Use compatible, disposable checkpoints with known initial receipt indices; the server starts fresh.

Optional ordered `stages` synchronize pickups with the other player's arrival. Each stage has a unique simple `name` and a `players` array containing conditions for both slots: `slot`, `capture` (a completed scenario capture event), `game` (`oot` or `mm`), `received_index` (exact, including zero), and optional `checks` (source checks already reported). Both ROMs must carry a valid mailbox directory. The coordinator requires a moving, connected mailbox at the destination's compiled address, the receipt index, capture and checks before writing `signal-<name>` into each isolated output directory. A scenario's bounded `wait_signal` step waits for that file. Gate the source interaction behind an arrival stage, then gate departure behind a stage requiring the actual check and receipt, to prove delivery occurred after arrival and before departure. Stage reports retain elapsed times and both observations. `wait_client` also works with this coordinator after ROM verification and a live receipt query. Both observers wait for the N64 ROM domain within a bounded startup window and reject a connector hash mismatch.

Optional `backlog` supplies a recipient `slot`, `disconnect_stage` and `checks` naming real expected sources in the other slot. Before releasing that stage's signals, the coordinator disconnects the recipient socket, notifies the game through its normal watcher and asserts the game's connected flag is zero. It suspends that recipient's watcher and repeatedly checks the socket and game stay disconnected while the other client reports the sources. Once all named checks are accepted, it requires the remote queue to have grown by exactly that many items and starts normal client login. Gate the recipient's next interaction behind a subsequent stage requiring the drained receipt index; the sender must be free to reach every backlog source without that stage. Reports retain the initial receipt index, queue lengths, offline observations and reconnect evidence, alongside the normal award, inventory and 16-poll stability assertions. This covers a controlled recipient outage while the server keeps running.

Optional `restart_stage` names a declared stage and cannot overlap a `backlog` outage. Before releasing its signals, the coordinator disconnects both clients, verifies both game connection flags clear, closes the listener, and saves the disposable server. It creates a new server context from the seed and saved bytes, verifies retained checks and remote queue lengths, and listens at the same address. Normal client login must restore live queries at the original receipt indices before gameplay resumes. Final assertions require new source checks and a higher remote receipt index for each slot, exactly one award per expected check, native scenario assertions and 16 fresh stable polls. Reports retain the pre-restart checks, queue lengths, indices and save hash; `before-restart.apsave` preserves the loaded snapshot. This is orderly listener/context replacement within the coordinator process, not process-crash coverage.

`--port` defaults to 43055. Each disposable connector retains its standard six-port Lua binding range; the second player's range starts ten ports later. Only copied connector files are changed. The coordinator services each client in an independent polling task, including while the other emulator starts or changes games, and reconnects within its own range. A slow connector must not delay the other game's mailbox service. Receipt stability requires fresh completed polls from both clients. `--timeout` bounds the whole run. A coordinator stop file lets each runner terminate its own emulator on failure. Standalone runs can use `gameplay_test.py --connector-port <range start>` and `--stop-file <path>` for the same isolation and cleanup behavior.

## Scenario format

A JSON scenario declares `coverage` (`unmodified-gameplay`, `assisted-gameplay` or `protocol`), `description`, `limitations`, `max_frames`, optional `probes` and ordered `steps`. For example, a matching child OoT checkpoint can be checked without modifying RAM:

```json
{
  "coverage": "unmodified-gameplay",
  "description": "Check the supplied child OoT checkpoint",
  "limitations": "No pickup, transition or victory is asserted",
  "max_frames": 300,
  "steps": [
    {"action": "wait", "frames": 30},
    {"action": "expect", "name": "child-age", "address": 1156564,
     "size": 4, "value": 1, "timeout_frames": 30},
    {"action": "capture", "name": "checkpoint"}
  ]
}
```

Actions:

- `wait`: advance `frames` with neutral controls.
- `speed`: set BizHawk's speed percentage with integer `percent` from 100 to 400 through `client.speedmode`. Scenarios containing this action enable clock throttling and clear unthrottled mode in their isolated configuration. Record frame and elapsed-time intervals to verify the achieved speed; demanding cores may run below the requested rate. Hold controller inputs across multiple video frames so they reach the game's update tick at either speed.
- `input`: hold digital `buttons`, such as `{"P1 A": true}`, and/or `analog`, such as `{"P1 X Axis": 80}`, for `frames`. Controls return to neutral between steps; analog values range from -128 to 127.
- `expect`: wait at most `timeout_frames` for a big-endian RDRAM value at `address` of `size` 1–4 to equal `value`. A `name` identifies failures. Optional `pointer` reads a KSEG0 pointer from RDRAM and treats `address` as its offset; invalid pointers fail the run.
- `wait_client`: wait at most `timeout_frames` for the observer's or coordinator's `client-ready.json`, written after a live mailbox query and ROM identity verification. Use it before leaving a restored checkpoint: its connected flag can still be 1 from the previous client. Requires the runner's server-observation arguments or an external coordinator. A fresh output directory prevents reusing an earlier ready file.
- `wait_signal`: wait at most `timeout_frames` for `signal-<name>` in the isolated output directory. Names use letters, digits, hyphens or underscores. The two-player coordinator releases these signals from its ordered stage assertions. Optional `dismiss_messages: true` presses B for eight frames every 60 frames while waiting, allowing queued item messages to finish through normal controller input; use a safe idle position and record the input assistance. In assisted scenarios, optional `keep_health: true`, `game` and `scene` refill health to the existing acquired capacity only while waiting; this requires a sourced, ROM-pinned layout and the active scene. Record this assistance when enemies can attack an idle player. Waiting otherwise makes no memory writes. Pausing is unsuitable for an arrival barrier because the game's item handshake does not complete while paused. Dismiss an incoming item message and reposition before the next source interaction.
- `wait_game`: wait at most `timeout_frames` for `game` (`oot` or `mm`) to have a valid play pointer, its sourced active main function and the requested `scene`. Requires that game's ROM-pinned layout. Unlike a pointer `expect`, this tolerates null and departing-game pointers during a switch. It logs `game_ready` when the destination payload matches; that alone does not establish a rendered frame, player control or client reattachment. Wait for the client's connected flag separately and allow rendering to settle before captures.
- `native_exit`: in assisted scenarios, approach an actual cross-game exit using sourced `game`, `scene`, `x`, `y`, `z`, `target_game`, `target_scene` and a bounded `timeout_frames`. Both layouts must be pinned to the input ROM. It holds the source position for 30 frames, then tries normal stick directions and action-button presses for 90 frames per approach. Position writes stop as soon as the source transition starts or its payload disappears; success requires the destination payload and scene. It never writes entrance fields, transition flags or mailbox packets. This bypasses travel and accounts for camera changes after a pickup; it does not establish the route or door-access requirements. Dismiss item dialogue and move normally away from the chest before approaching the exit.
- `capture`: write a PNG, state and named probe values using a simple filename `name`.
- `oot_transition`: require `from_scene`, set `entrance` through OoT's normal transition fields. This prepares a scene; it does not prove the route or a cross-game entrance works.
- `oot_position`: require `scene`, place the player at `x`, `y`, `z`, including the previous position used by collision sweeps. Optional `frames` (1–60, default 1) holds the setup across frame boundaries before releasing it. Optional unsigned 16-bit `yaw` sets actor world/shape facing; animation can update it again, so use controller input for interactions. It does not open a chest or change flags.
- `mm_transition` and `mm_position`: the corresponding helpers using MM's play-state and actor-list layout.
- `boot_file`: wait for normal OoT game mode and the requested `scene`, cycling file-menu inputs until gameplay or `timeout_frames`. Requires the matching sourced OoT layout; title-screen play state alone is not gameplay evidence.
- `mm_boss_support`: supply a bounded `frames` count while in Majora's arena (scene `11`). Refill health to the existing capacity and magic to the existing acquired level each frame; lower each live main phase to one health once. Stops on arena/payload exit or at the frame limit. Does not touch damage, death, completion or mailbox state.
- `mm_boss_approach`: while boss support is active, position and face Link behind a live main Majora phase, updating current and previous position. Airborne placement is allowed. This skips movement and targeting difficulty; normal attacks still have to connect. After support stops it makes no writes.
- `oot_boss_loadout`: require `scene` and a previously acquired Master Sword; prepare twenty hearts and the adult sword loadout, then request adult age through `PlayState.linkAgeOnLoad`. Follow immediately with a scene transition so the native age/equipment swap runs. Does not grant the sword or change its found flag.
- `oot_boss_support`: bounded `frames` in Ganon's arena (scene `79`); refill existing health capacity and lower native health values `30` and `25` once each. Stops on arena/payload exit or timeout.
- `oot_boss_arm`: equip an acquired `master` or `biggoron` sword for the isolated fight. Clears only the native swordless equipment state; does not change boss progress. This skips the equipment menu and requires the sword's real item-grant path beforehand.
- `oot_boss_weapon`: approach the native dropped sword effect after first-phase damage has reduced Ganon's health to zero or below. The game handles proximity pickup and recovery; premature pickup can invalidate the fight sequence.
- `oot_boss_approach`: while support is active, position Link at the native tail collider, or at ground level near the head for the final blow. Normal sword attacks and the native final-blow handler remain required.
- `mm_boss_loadout`: require `scene` and human Link, then supply a Gilded Sword, Fierce Deity mask on C-left, twenty hearts and double magic, filled once. This fixed developer setup uses v33.0's native save layout; it does not transform Link, refill during combat, change boss health or write completion flags. Use normal controller input to transform and fight.

All setup actions require `coverage: assisted-gameplay`, an exact `required_rom_sha256`, and the corresponding `oot_layout` or `mm_layout` containing `play_pointer` (RDRAM address of `gPlay`), `main` (KSEG0 address of `Play_MainWrapper`) and a `source` description. Resolve these from the **matching** compiled payload with `nm`; they can move between builds. Helpers check the active main function, valid play pointer and scene. Position/loadout helpers also validate the player actor; boss interaction helpers restrict actor IDs and validate interaction pointers before writing. Transitions must be idle. Actor captures record positions, IDs, categories, chest parameters and the generic collision-health byte for locating interaction points. Collision health is diagnostic only: some actors keep a separate health field, so it is not a boss-defeat assertion.

Field sources for v33.0 are `packages/generator/include/combo/game_state.h`, `combo/oot/play.h`, `combo/mm/play.h`, `combo/oot/actor.h` and `combo/actor.h`; `src/link_oot.in` and `src/link_mm.in` define native save addresses. `data/defs/entrances.yml` and `scenes.yml` define destination entrances and scenes. The position helper uses the player category's actor-list pointer and `Actor.world.pos` and `Actor.prevPos`. The transition helper uses `nextEntrance`, `transitionType` and `transitionTrigger`, as the game's own transition callers do. Never copy compiled addresses from a different ROM.

Keep the generic connector running in scenarios. Do not add frame-advance loops inside scenario callbacks: the connector owns frame advancement. Every wait needs a frame or wall-clock bound. Check failure screenshots and logs before treating an assertion as a game bug.

Before a physical pickup, dismiss any asynchronous remote-item dialogue and establish the intended facing with controller input. A pending item message can consume the interaction button while the chest remains closed. Use the server's exact source-check assertion to detect this; a completed input sequence or received-item message is insufficient. For game-switch performance comparisons run the client-attached and unattached scenarios sequentially, without other emulators or generation tests competing for CPU, from identical ROM/checkpoint/configuration inputs. Record the controller-input-to-`game_ready` interval and mailbox recovery separately. The observer records `rom_mailbox_directory` so direct lookup can be distinguished from fallback scanning. Loss-to-reattachment includes any native loading after loss, connector reconnects and heartbeat sampling; it is not solely discovery overhead. For direct lookup, check that both observed live addresses match the directory and that the native transition intervals remain comparable to the unattached control.


### Boss checkpoint requirements

Use `OOT_BOSS_GANON2` (`0x517`) and `MM_BOSS_MAJORA` (`0x0200`) from the tracked `data/defs/entrances.yml` when preparing isolated arena checkpoints. Entering a scene alone does not establish a valid fight state. In `src/oot/play/play.c`, the Ganon entrance redirects to Ganon Tower unless `comboHasSoulOot(GI_OOT_SOUL_NPC_ZELDA)` succeeds and `gSharedCustomSave.foundMasterSword` is set. Prepare those prerequisites through their real item-grant path before asserting an arena entry; do not bypass the redirect or write boss completion flags.

OoT's `endGame` sends the self Triforce through `Multi_SendSelfItem` when the real ending transition reaches `ENTR_OOT_SAGES_CHAMBER_END`. MM's end-of-game branch in `src/mm/play/play.c` sends the self Majora mask. Both use persistent NPC bitmaps to avoid duplicate sends. A victory test must exercise the actual fight and ending transition, observe the corresponding client goal and server storage, then preserve the native and server saves for restart checks. Calling either helper or writing its flags directly provides protocol coverage only.

The read-only actor collision-health samples use `Actor.colChkInfo.health` from `combo/actor.h` and `combo/common/collision_check.h` (`0xaf` in OoT, `0xb7` in MM). Verify an individual boss's implementation before adding a health shortcut: the shared structure explicitly permits actors to keep health elsewhere. Majora support is restricted to actor `0x12f`, boss category `9`, types `10`, `20` and `30`: the original [Boss07 implementation](https://github.com/zeldaret/mm/blob/main/src/overlays/actors/ovl_Boss_07/z_boss_07.c) uses this health byte in `Boss07_Mask_SetupDamaged`, `Boss07_Incarnation_SetupDamaged` and `Boss07_Wrath_SetupDamaged`. The [type definitions](https://github.com/zeldaret/mm/blob/main/src/overlays/actors/ovl_Boss_07/z_boss_07.h) distinguish main phases from projectiles, afterimages, remains and the battle handler. OoTMM v33.0's Boss07 C patch wraps the top-spawn call, and its assembly patch shortens introduction sequences; the native damage handlers remain. Health zero/negative is left to normal damage and phase handling.

The fixed MM loadout uses `MmSave.info` at `0x24`, `MmSavePlayerData`, `MmItemEquips` and `MmInventory` in `combo/mm/save.h`; `src/link_mm.in` places `gSaveContext` at `0x801ef670`. Sword ID `0x4f`, Fierce Deity mask ID `0x35` and mask slot `0x2f` come from `combo/data/items.h`. Human form (`4`) is required before writing equipment. Transformation remains an input-driven action; form `0` is Fierce Deity. These supplies are diagnostic assistance and do not verify item delivery.


Ganon setup uses `Age_SetRawOot`/`Age_OnChangeOot` in `src/common/age.c`, `linkAgeOnLoad` at `0x11de8` in `combo/oot/play.h`, and the adult equipment at `0x4a` in `combo/oot/save.h`. `eventsMisc[29]` is the swordless equipment state in `combo/common/events.h`. The original [Ganon implementation](https://github.com/zeldaret/oot/blob/main/src/overlays/actors/ovl_Boss_Ganon2/z_boss_ganon2.c) uses collision health, joint-sphere element 15 for tail damage, and the head position for the final-blow distance/facing test. Its [structure header](https://github.com/zeldaret/oot/blob/main/src/overlays/actors/ovl_Boss_Ganon2/z_boss_ganon2.h) documents a debug Actor with an extra `0x10` bytes; retail OoT 1.0 has no debug pad. The helper therefore reads the collider at `0x414` and head at `0x1a8`, with native collider dimensions from `combo/oot/collision_check.h`. Sword-effect positioning uses `PlayState.specialEffects` at `0x11e10`. None of these actions writes a victory flag or emits a boss packet.
