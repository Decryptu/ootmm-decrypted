# Working on OoTMM Decrypted

Everything a new contributor needs, with no other context. Keep it current. [ROADMAP.md](ROADMAP.md) lists what is in progress and planned.

## What this is
- A continuation of [Quasky/AP-OOTMM](https://github.com/Quasky/AP-OOTMM): an Archipelago world (`OOTxMM`) for the [OoTMM](https://github.com/OoTMM/OoTMM) combo randomizer.
- OoTMM's own data (world graph, conditions, items, settings) is converted into the world's metadata by `raw/GenerateMetadata.py`, so logic follows OoTMM instead of being written by hand.
- The repository root is the world package. `tools/build_apworld.py` picks the files that go into `ootxmm.apworld`; everything else (tools, these docs, the generator and its intermediates) stays out.

## Metadata
`raw/GenerateMetadata.py` is the single place OoTMM data is converted. To regenerate:
1. Put an OoTMM checkout of the release we track ([ROADMAP.md](ROADMAP.md#decisions)) in `raw/ootmm` (ignored by git): `git clone --depth 1 --branch v33.0 https://github.com/OoTMM/OoTMM.git raw/ootmm`. Name the release in the commit message.
2. From `raw/` (the script uses relative paths), run `python GenerateMetadata.py`. It needs PyYAML, and Node with pnpm and the checkout's installed `tsx`: the logic, item and settings steps import OoTMM's TypeScript directly. The script first installs the checkout dependencies, then uses its local TypeScript runner; the logic step builds its data package.
3. It merges `data/world` and `data/macros` into the `Great*` dumps, exports the settings and sorts them ([Options](#options)), exports the logic, updates the location ID registry (below), exports each check's vanilla item and what OoTMM places before its fill ([Placement](#placement)), exports the items and updates their registry, splits out the `Isolated*` files, converts the offered settings into `GeneratedOptions.py` and copies that over `../options.py`. Any error stops it.

What the world data looks like, and why:
- **Default variant only.** `WorldSources` lists the files OoTMM's `packages/data/build/world.ts` loads for default settings: no `dungeons_mq` (Master Quest) and no `mm/jp` (the `jpLayouts` Deku Palace). Those files reuse the vanilla region names, so they can't share one dump.
- **Game prefix.** OoT and MM reuse names (shops, `GLOBAL`, `VOID`), so every region and location is named `OOT <name>` or `MM <name>`, like OoTMM's internal IDs. An exit that already starts with a prefix points into the other game. The spawn is `OOT SPAWN`.
- **Reachable regions only.** Regions no exit chain reaches from `OOT SPAWN` are dropped and printed: stubs for the other Deku Palace layout, entrance-randomizer-only sources, and data OoTMM never connects (in v33.0, `Pirate Fortress Telescope` has `exit:` instead of `exits:`).
- **Macros** stay split as `common`, `OOT` and `MM`, since the same macro name differs per game. They are kept for reading: the world uses the logic dump, where OoTMM has already inlined them.

## Logic
OoTMM's own code turns its conditions into rules, so nothing is parsed or rewritten by hand. The generator runs OoTMM's pipeline with default settings up to the entrance pass (which links the games: the Mask Shop door leads to Clock Town) and writes every exit, check and event condition into `raw/GreatLogicJSONdump.json` as a node table. Macros, song events and settings the world does not offer are already decided there. Price predicates retain their slot and wallet threshold. The world transform pass is skipped, because it drops the checks default settings leave out and this world keeps them.

The offered settings conditions read (the `logic` and `ported` classes in [Options](#options)) and every trick stay symbolic: OoTMM's parser decides `setting(...)` and `trick(...)` on the spot, so the export wraps its `parseExprSetting` and `parseExprTrick` to return marker events instead, and parses `!` and `cond(...)` itself, since OoTMM only allows them on settings it has decided. The dump has `setting`, `trick` and `not` nodes for them, which `logic.py` decides from the player's settings. Enum values excluded by `OfferedValues` are false during export, so unsupported branches do not introduce requirements such as custom special conditions.

`logic.py` builds the graph from it for each player's settings (`logic.build`, shared by players whose logic settings and tricks match):
- **Ages.** OoTMM explores every area as child and as adult, so each region has a `(Child)` and an `(Adult)` copy, and conditions are specialized to the copy's age. Both ages start at `OOT SPAWN`, the origin, as in OoTMM's pathfinder; the adult spawn needs the `OOT_TIME_TRAVEL` event. Age change at will (`ageChange`) defaults to `none`; `oot` requires the Ocarina of Time and `always` accepts the Fairy Ocarina. Both require the Temple of Time time-travel event and Song of Time. Once unlocked, age connections exist only in OoT areas whose exported `age_change` permits them; the time traversal carries clocks and route flags to the other age and revisits reached areas when the event unlocks. MM never gains these connections. The pool stays unchanged because non-default `itemPool` modes are unavailable.
- **Events** become event items placed on locations named after them (`MM_MAJORA`). The completion condition follows `goal` (below).
- **Impossible conditions are false**, as they are for OoTMM: an item the pool never holds (MM Ruto's Letter) or an event no area triggers (the pre-completed dungeon events). The pool is the vanilla items of the checks that exist, and which checks exist depends on the pool, so `logic.py` starts from every item and drops those whose check is unreachable until it settles.
- **Left out:** region copies no exit reaches with every pool item, checks and events false at every copy, and empty terminal areas left by check filters. In v33.0 with default settings 34 checks are impossible (MM underwater rocks without MM iron boots, child silver boulders, the guarded Hyrule Castle tree), all unreachable in OoTMM too with default settings.
- **Several parents.** OoTMM lists some checks and events under several regions, meaning reachable from any of them, and every age copy is a parent. Archipelago gives a location one region, so `locations.py` gives a check with more than one parent its own `<check> (check)` region (`<event> (event)` for events), with an entrance from every parent that carries that parent's condition.
- **Time and regional constraints.** The metadata preserves OoTMM's time predicates, OoT area clock modes, MM's 46 time slices, conditional waiting rules and regional flag constraints. `time_logic.py` propagates these per area and age, following OoTMM's `pathfind/pathfind.ts` and `expr/compile.ts`: exits restrict the ranges they carry, waiting expands them where allowed, and an OoT-to-MM transition adds day-one 06:00. It derives reachable events alongside the ranges. Access rules consult this traversal; the graph's initial pruning remains optimistic about time so it does not remove checks or their items. Waiting conditions contribute to progression classification. Inventory snapshots cache results independently of AP's event sweep. Item gains revisit dependent areas using an earlier result; item removal starts a fresh traversal. State copies use the result for their own inventory. `test/time_samples.json`, regenerated by `GenerateTimeSamples`, compares area clocks with OoTMM's original pathfinder under five inventories for each `ageChange` mode; focused tests cover late entry, conditional waiting, conflicting times and flags, cache invalidation, and incremental versus fresh traversal.
- **Approximations.** `renewable(x)` and `license(x)` count as having `x`.
- **Progression** items are the ones some condition of the player's graph asks for (`Logic.items`). An item link group's world has no graph of its own: its progression items are its members'.

## Options
OoTMM has over 500 settings, and most change more than conditions: the pool, which checks exist, the shape of the world. The world offers only the ones it handles, and `ClassifySettings` in `raw/GenerateMetadata.py` decides which by scanning OoTMM's source, so a new OoTMM release is classified again without a hand-kept list. Its result is `raw/SettingsClasses.json`:
- **ported**: OoTMM's code reads it outside conditions, and the world does what that code does. Listed by hand in `Ported` in `raw/Meta_Options.py`. Offered, and symbolic in the logic dump.
- **port**: OoTMM's code reads it outside conditions (`packages/logic/src`, `packages/data/build`, `packages/core/src`, except the files that only define, parse or roll settings). Not offered until the world ports what it does there ([ROADMAP.md](ROADMAP.md)).
- **logic**: only conditions read it (`setting(...)` in `data/`). Offered, and symbolic in the logic dump ([Logic](#logic)).
- **patch**: neither reads it, so only the ROM patcher does. Offered and passed through.
- **not_offered**: listed in `raw/Meta_Options.py`: meaningless in a multiworld (players, hints, spoiler), read through computed keys the scan can't see (`items.mmAgeRequirements`), or a `custom` value that needs `specialConds`, which is not ported (`lacs`, `rainbowBridge`, `majoraChild`).

The tricks are one option set, `tricks`, defaulting to OoTMM's default tricks. Options are named by their OoTMM key (`doorOfTime: open` in a player YAML), grouped by OoTMM's categories. Archipelago lowercases Choice names and reserves `random` (it rolls it itself, so OoTMM's own `random` value is skipped except for shop prices, which expose it as `uniform`, and a `random` default becomes `default = "random"`); each Choice keeps OoTMM's values in `ootmm_values`. `ootmm_settings` in `world.py` turns a player's options back into OoTMM settings, which `logic.build` reads and `fill_slot_data` hands on as `settings`, for the patch.

Settings the world doesn't offer keep OoTMM's default (`defaults` in `raw/GreatSettingsJSONdump.json`).

**Ported so far: the check filters, shops and shop prices, goal, Song of Time age changing, Tingle maps and map/compass, regular and Hideout/chest-game small-key, boss-key (including Ganon), stray-fairy, song and blue-warp, dungeon-only (with or without a one-reward limit) and anywhere reward placement, plus optional vanilla OoT ocarina, Master Sword and Gerudo Card placements, separate and shared skeleton keys, small-key rings, enemy, boss, NPC, animal and miscellaneous souls, including shared souls, separate or shared ocarina buttons, and shared bows, bomb bags, magic, elemental arrows, Hookshot, Lens of Truth, Epona, Storms, Time, Sun, Elegy, Healing, Soaring, Awakening, New Wave Bossa Nova, Oath to Order and Goron Lullaby songs, and Goron, Zora, Truth, Bunny and Keaton masks.** OoTMM leaves out the checks a setting doesn't shuffle (pots, grass, rocks, free rupees and the like, `filterChecks*` and the removals before `makePools` in `run()` of its `world/transform.ts`); the world's checks are its world files' checks minus `removed_checks` in `logic.py`. That reads each check's type, scene and whether the scene is a dungeon from `raw/GreatCheckInfoJSONdump.json`, which the generator exports from OoTMM's check data along with the name lists `transform.ts` removes by. A removed check's vanilla item leaves the pool with it, as in OoTMM. `pondFishShuffle` is not ported: it also puts fish of random weights in the pool.

`shopShuffleOot` and `shopShuffleMm` offer `none` and `full`. Full removes the game's ordinary shops from fixed placement; MM's two bomb-bag purchases and All-Night Mask remain shuffled in either mode, as in OoTMM. The exporter derives `shopFixed` from upstream's fixer and samples all four shop-toggle combinations. Items and check counts stay unchanged with the default pool.

`priceOotShops` and `priceMmShops` offer `vanilla`, `affordable` (10 rupees), `weighted` and `uniform` (OoTMM's `random`). Archipelago reserves `random` for rolling an option, so use `uniform` for uniformly random costs; the hub translates imported OoTMM settings automatically. `prices.py` follows OoTMM's five-rupee draws and weighted order statistic, using Archipelago's player RNG. Wallet settings set the price range. Each player's table specializes the exported price predicates before reachability pruning and forms part of the graph cache key. `generate_output` writes the same table for the ROM builder; missing tables with changed shop prices and malformed tables fail patching. Scrub, merchant and Tingle prices retain defaults. Older vanilla-price placement files remain supported. Upstream reference samples compare clocks and shop reachability at every price mode with and without wallets. Existing `renewable`/`license` inventory approximations still apply to shop logic; native shuffled purchases and remote awards remain gameplay gates.

`shuffleOcarinasOot`, `shuffleMasterSword` and `shuffleGerudoCard` default on, matching OoTMM. Turning one off keeps its existing checks and locks their vanilla equipment locally before the main fill: both OoT ocarina pickups, the Temple of Time Master Sword, or the Gerudo membership card. No equipment copy is added or removed. `GenerateFillFile` obtains these conditional placements from OoTMM's own fixer under all eight toggle combinations, exporting `conditionalFixed` and `test/fixed_samples.json`. The reference test compares the complete fixed-check sets with OoTMM, and generation tests check locked local items and their absence from the main pool. Unsupported pool modes and adult starts remain unavailable.

Base and optional extra items enter the pool before shared replacements, so OoT masks without vanilla checks are converted together with their MM counterparts. Logic pruning uses the same combined pool.

Shared equipment and songs apply the ordered `replaceItem` and `removeItem` operations exported from OoTMM's `world/transform.ts` into `poolTransforms`. The combined pool keeps three shared bows, three shared bomb bags, two shared magic upgrades and two shared Hookshots; each shared elemental arrow, Lens of Truth and Epona, Storms, Time or Sun song has one copy. Shared Goron, Zora, Truth, Bunny and Keaton masks each retain one copy in the combined pool. Goron and Zora masks provide their transformation abilities in MM; their OoT counterparts are cosmetic. Shared songs retain the `songs` placement restriction. Ammunition, magic jars and fixed vanilla pickups use the same replacements; removed upgrade copies become filler. Logic pruning uses the transformed pool and caches each setting independently. The exporter preserves v33.0's arrow replacement order: its first replacement maps OoT 30-arrow bundles to shared 5-arrow bundles. Follow the tracked release when changing it. `GenerateEquipmentSamples` records independent results from OoTMM's full world pipeline in `test/shared_equipment_samples.json`; the reference test compares every affected item count for the separate and combined settings.

Cross-game song settings add one separate song in the receiving game, or replace the native copy with one shared song when sharing is enabled:

| OoT enabling setting | Shared setting | Song |
|---|---|---|
| `elegyOot` | `sharedSongElegy` | Elegy of Emptiness |
| `songHealingOot` | `sharedSongHealing` | Song of Healing |
| `songSoaringOot` | `sharedSongSoaring` | Song of Soaring |
| `songAwakeningOot` | `sharedSongAwakening` | Sonata of Awakening |
| `songZoraOot` | `sharedSongZora` | New Wave Bossa Nova |
| `songOrderOot` | `sharedSongOrder` | Oath to Order |

Sharing is disabled when the corresponding enabling setting is off, matching OoTMM's settings validation. The exporter records these dependencies and pool additions alongside the ordered replacements. Extra separate songs need room in the song-location pool: use `songs: anywhere` or share enough other songs. The same song-placement rules apply to separate and shared copies. Tests verify the shared Sonata opens Woodfall Temple, the shared Bossa Nova wakes the turtle and the shared Oath opens the Moon under the native MM conditions.

`songSunMm` enables a separate MM Sun's Song; `sharedSongSun` instead replaces the existing OoT song with one shared copy. Sun sharing is disabled unless its MM enabling setting is on. The same pool, placement and capacity rules apply in either direction. Native song use in the additional game remains a gameplay gate.

Goron Lullaby has separate rules. `songGoronOot` enables an OoT copy; `progressiveGoronLullabyOot` and `progressiveGoronLullabyMm` select `progressive` (two Intro items, the second granting the full song) or `single` (one full Lullaby). Both default to `progressive`. `sharedSongGoron` replaces the MM copies with shared ones and adds no OoT copies; sharing is disabled unless OoT is enabled and the modes match. Single MM mode keeps the Goron Baby check but excludes it from song placement and from song-location capacity; it becomes available for other items. Pool transforms run even with no sharing enabled, so the default MM pool also matches OoTMM. The source-reference samples cover every combination of enabling, sharing and both modes, including the eligible song checks. Native progressive receipt and song use remain gameplay gates.

`goal` sets the completion condition in `rules.py` as OoTMM's `isGoalReached` does, from its `OOT_GANON` and `MM_MAJORA` events. An enum can be offered with only some of its values (`OfferedValues` in `raw/Meta_Options.py`): `goal` leaves out the Triforce values, which add pieces to the pool.

To port a setting: do in the world what OoTMM's code does with it, add it to `PortedChecks`, `PortedGoal`, `PortedDungeon`, `PortedFairies`, `PortedSongs`, `PortedRewards`, `PortedMaps`, `PortedPool`, `PortedFixed`, `PortedTraversal` or `PortedShops` in `raw/Meta_Options.py` (or a new list for a new kind), and rerun the generator. `test/test_checks.py` checks that every ported setting is one the check filters, completion condition, pool additions, key-ring conversion, age traversal, price generation or item placement handles (`PORTED_SETTINGS` in `options.py`) and checks that `removed_checks` leaves exactly OoTMM's own checks for the settings in `test/check_samples.json`. The generator writes that file by running OoTMM's pipeline with defaults, then every ported check setting at `all` (or on), `overworld` and `dungeons` (or off), as hashes of the check names; on a mismatch, compare `removed_checks` with OoTMM's `state.worlds[0].locations` for that sample. `test/test_options.py` generates with non-default settings and all tricks, and `test/test_checks.py` also generates with every ported setting on.

## Items
`raw/GenerateMetadata.py` exports OoTMM's item list (`packages/logic/src/items/defs.ts`) with each item's display name (`packages/generator/lib/combo/names.ts`) and whether it is in the `TRAPS` or `JUNK` group (`groups.ts`) into `raw/GreatItemJSONdump.json`, with the GI the game gives each item by (`gi()` in OoTMM's `generator/lib/combo/randomizer/util.ts`, for OoTMM's defaults of the settings it reads, none of which the world offers; shared items as their OoT version), which the client sends received items as. `items.py` makes traps `trap`, items the logic asks for `progression`, junk `filler` (including `Nothing`, OoTMM's empty check) and everything else `useful`.

- **Names.** Archipelago needs unique item names, and OoTMM reuses some (`Blue Fire` is an OoT, an MM and a shared item). A reused name gets ` (OoT)` or ` (MM)` on the game's own items, so the shared item keeps the plain name; one still reused gets its OoTMM ID added (`5 Deku Nuts (OoT) (OOT_NUTS_5_ALT)`). The generator fails if any name is still reused.
- **Pool.** OoTMM's base pool: the vanilla item of every check, plus the items whose vanilla source is not a check (`EXTRA_ITEMS` in `logic.py`, from OoTMM's `world/transform.ts`), which replace random filler so the pool matches the location count. The generator exports each check's vanilla item from OoTMM's `data/checks` XML into `raw/GreatCheckItemJSONdump.json`, swapping the placeholders OoTMM swaps itself (`OOT_RANDOM` and the like become green rupees, `CheckItemAliases`), and fails if a location has none. Skeleton keys, ocarina buttons, enemy, boss, NPC, animal and miscellaneous souls are optional additions and selected small keys become rings. Shared equipment and songs also replace their original items and consumables; other option-dependent pool changes are not ported yet ([ROADMAP.md](ROADMAP.md)).
- **Skeleton keys.** `skeletonKeyOot` and `skeletonKeyMm` each add one game-specific skeleton key, replacing filler and retaining ordinary small keys, as OoTMM's transform does. `logic.extra_items` supplies these additions to both graph specialization and pool creation. Pool settings are part of the graph cache key because adding an item preserves routes that would otherwise be pruned. Keys remain in the main pool and can be sent across worlds; their game-specific door conditions come from OoTMM's macros. Both options default off. `sharedSkeletonKey` merges the two additions into one shared key that opens both games' doors; it is reset to false unless both game-specific options are enabled. Ordinary keys remain in the pool.
- **Small-key rings.** `smallKeyRingOot` and `smallKeyRingMm` are sets of dungeon identifiers (listed in the generated option descriptions), empty by default. Each selected dungeon's small keys become one ring, with freed slots filled by random filler. Removed keys produce no ring. Hideout and Treasure Chest Game ignore ring selection when their key placement is `vanilla`. Rings follow their keys' placement setting: local pre-fill under `ownDungeon`, unrestricted under `anywhere`. The exported `dungeonShuffleItems` lists include both small keys and rings so unrestricted rings leave the dungeon pre-fill. `logic.key_rings` shares conversion with pool creation; set membership specializes OoTMM's ring conditions, and canonical selections and Hideout placement distinguish graph cache entries. The ROM patch converts list settings to OoTMM's specific-set format.
- **Souls.** `soulsEnemyOot` and `soulsEnemyMm` add one of every enemy soul in the respective OoTMM group, replacing filler. `soulsBossOot` adds the eight OoT dungeon-boss souls; `soulsBossMm` adds the four MM temple-boss souls and Igos du Ikana. `soulsNpcOot` and `soulsNpcMm` add one of each NPC soul in their respective groups. `soulsAnimalOot` and `soulsAnimalMm` each add four animal souls (cucco, cow, dog and butterfly); `soulsMiscOot` and `soulsMiscMm` each add Gold Skulltula and business-scrub souls. These settings default off. `GenerateFillFile` exports these groups as `optionalItems`; `logic.extra_items` uses them for both graph specialization and pool creation. OoTMM's symbolic conditions gate enemy encounters, boss defeats, NPC and animal interactions, Gold Skulltulas and business scrubs on the matching soul; required souls are progression and can travel across worlds. Large additions require enough shuffled checks: enabling both games' enemy souls with otherwise default settings exceeds the available filler slots. Enable more check shuffles, such as `shufflePotsOot: all` and `shufflePotsMm: all`; generation reports the available and required slots if the pool cannot fit.
- **Shared souls.** `sharedSoulsEnemy`, `sharedSoulsNpc`, `sharedSoulsAnimal` and `sharedSoulsMisc` merge matching souls into one shared copy, following OoTMM's `shareItems` maximum-count policy. Souls unique to one game and boss souls remain separate. `GenerateFillFile` exports upstream's pairings as `sharedItems`; pool creation and graph specialization use the same merged additions. As in OoTMM, sharing is reset to false unless the family is enabled in both games; normalized settings are also exported to the ROM builder.
- **Ocarina buttons.** `ocarinaButtonsShuffleOot` and `ocarinaButtonsShuffleMm` each add the five buttons (A and the four C directions), replacing filler. `sharedOcarinaButtons` merges both sets into five shared buttons and is reset to false unless both shuffles are enabled. All three settings default off. Upstream's button pairings supply both the `optionalItems` additions and `sharedItems` conversion metadata. The symbolic song, scarecrow and minigame conditions require the appropriate buttons; these items remain in the main multiworld pool. The ocarinas and songs themselves retain their existing placement settings.
- **Removed.** Items OoTMM takes out of the pool with the settings in use become random filler (`removed_item` in `prefill.py`): Ganon's boss key, as `ganonBossKey` defaults to `removed`, and maps, compasses or regular dungeon keys when their shuffle setting is `removed`.
- **IDs** live in `raw/ItemIDs.json`, a registry keyed by OoTMM's item ID that follows the same rules as the location registry below: OoT `1001-1999`, MM `2001-2999`, shared `3001-3999`. Item and location IDs are part of the multiworld protocol: once a release is out, never renumber them. `items.py` fails at import if an item has no ID.

## Placement
Unported item placement settings keep OoTMM's defaults. The ROM must match each player's placement settings: under `ownDungeon` a check in a dungeon gives a key for that dungeon whichever key was placed there, and a shop or cow that isn't shuffled gives its vanilla item. So the world places these items as OoTMM's solver (`packages/logic/src/solver/solve.ts`) does before its main fill, in `prefill.py`:
- **Fixed checks** keep their vanilla item (`place_fixed`): the checks OoTMM's fixer (`misc/fixer.ts`) marks, such as shops, scrubs, cows, merchants, gold skulltula tokens, silver rupees, stray fairies set to `vanilla` and the chest game keys.
- Under the default settings, **dungeon rewards** go to the bosses and the Temple of Time (`dungeonBlueWarps`), then **songs** to the song checks (`songLocations`), then each dungeon's **keys, boss key, map, compass and own-dungeon stray fairies** to its own checks (`DUNGEON_ITEMS` in `solve.ts`; Stone Tower's also to Inverted Stone Tower, Ganon's Castle's also to Ganon's Tower). `pre_fill` places each group with Archipelago's `fill_restrictive` and starts over (up to `ATTEMPTS`) if the greedy fill corners itself. OoTMM places songs before rewards; rewards go first here, because 13 rewards for 13 checks is the tighter fit and the greedy fill fails far less that way. The groups' items stay out of the pool (`split_pool`) and reach Archipelago through `get_pre_fill_items` until placed.

`dungeonRewardShuffle` offers `dungeonBlueWarps` (the default), `dungeonsLimited`, `dungeons` and `anywhere`. Blue-warp mode pre-fills the 13 rewards locally at the boss and Temple of Time reward checks. Anywhere mode keeps all 13 in Archipelago's main pool, including other players' worlds. Dungeon-only mode keeps rewards out of the main pool and uses `stage_pre_fill` after all local groups are placed, allowing rewards in any OoTMM player's eligible dungeons. Eligibility comes from OoTMM's reward dungeon lists, includes Inverted Stone Tower with Stone Tower, excludes Ganon's Castle/Tower and the Moon, and excludes reserved song checks according to the host player's settings. All modes preserve the 13 rewards and their checks. `dungeonsLimited` reserves each host dungeon containing a limited reward against every other dungeon reward, including remote and later anywhere-mode rewards. In mixed settings, unrestricted rewards can share dungeons that contain no limited reward. Stone Tower and its inverted layout count as one dungeon. The plentiful item pool remains unavailable.

`songs` offers `songLocations` (the default) and `anywhere`. Song-location mode pre-fills songs locally at song checks; anywhere mode leaves every song in Archipelago's main pool, allowing checks in other players' worlds. Both modes keep the same song counts and checks. Individual song notes (`notes`) are not offered because they require replacing songs with note items. Epona, Storms, Time, Sun, Elegy, Healing, Soaring, Awakening, New Wave Bossa Nova, Oath to Order and Goron Lullaby can each be shared between games; shared copies follow the same placement mode. ## Client
`client.py` is a client on Archipelago's BizHawk connector (`worlds/_bizhawk`; the player runs Archipelago's BizHawk Client and the connector Lua script in BizHawk). It talks to the game through the RAM mailbox of our OoTMM patch ([Our OoTMM changes](#our-ootmm-changes)) in OoTMM's own multiworld protocol (`src/common/multi/multi.h` and `multi.c` in OoTMM):
- **Finding the mailbox.** New patches carry a versioned mailbox directory in reserved N64 ROM-header bytes: `APIPC001` at `0x18`, followed by the OoT and MM RDRAM offsets as two big-endian 24-bit values at `0x34` and `0x37`. `ap-patch.ts` takes these from each compiled payload's exported `AP_IPC_MAILBOX` symbol and writes them into `oot/makerom`, so standard v33.0 CLI/browser Patch mode preserves them. The ROM title, cartridge ID, entry point and checksum fields are untouched. The client validates distinct, aligned offsets with room for both rings, then reads only the two 24-byte headers per discovery poll. A directory address alone never permits a write: the magic must match and its `alive` counter must move between polls. Both games are watched together, so an intact stale mailbox cannot delay the other game's first attachment. Known addresses and directory offsets are discarded on ROM validation, while mailbox resets preserve the current ROM's directory. Without a recognized valid directory, discovery scans RDRAM in four 32 KB reads per poll and remembers live addresses; after losing a mailbox it waits up to 20 seconds at remembered addresses before scanning again. This fallback supports existing patches; it does not give them the direct-lookup speedup. Three empty scans warn that the ROM was not built from an `.ootmm` patch.
- **Mailbox liveness.** The magic also exists as a string constant in the code, and the other game's mailbox may remain in RAM after switching. Only a moving counter proves a live mailbox. It moves in gameplay (`Multi_Update`), not on the title screen or file select. A three-second stall restarts discovery, even if magic and `connected` remain intact. Paused emulation reattaches after resuming; boss progress survives rediscovery. The client sets `connected` after discovery and clears it on server loss, so the game keeps its pending checks. Every mailbox write is guarded by the magic because a game switch can put unrelated data at the old address.
- **Fresh attachment.** A newly discovered mailbox is first marked disconnected. The client waits for its `alive` counter to change before reconnecting, so a restored game or an unclean client exit cannot retain the previous session's packet sequence. A stalled counter times out into discovery. Queued queries cannot establish a session before the game sends its hello; unacknowledged reliable checks are resent after the handshake.
- **Handshake.** The game sends HELLO every 30 frames until it reads an answer; the client answers the latest one with `seqNet` 1 and numbers its own packets from there. The game checks that numbering and drops the connection on a gap.
- **Checks.** The game sends a WAL item packet for every check the player gets, their own items included, with the check's key; the client acks it (the game waits for that ack before its next pickup) and reports the location (`keys` in `raw/GreatCheckInfoJSONdump.json`). Beating Ganon and Majora also arrive as WAL items to the player's own world, with the full Triforce's and Majora's Mask's GI (`goalGi`), which is how the client sees the goal.
- **Received items.** The game asks every frame for WAL index `walIndex` (kept in its save). Index `i` is the `i`-th item the server sent: items from other worlds and the starting inventory (`items_handling` 0b101; the game gives the player's own pickups itself). The client sends it as coming from world 2, so the game doesn't take it for one of its own pickups, with the sender's name.
- **Delivery and retries.** Before acknowledging a check, the client adds it to CommonClient's `locations_checked` retry set and submits it to the server. CommonClient resends this set on login, including checks collected when the socket closes during a poll. If the game's incoming ring cannot fit a reply batch, the client leaves the outgoing batch and its packet sequence untouched until space is available. `test/test_client.py` covers a closed socket, a failed send, ring exhaustion and wrapped replies.
- **Timing.** The game drops the connection when its 2 KB outgoing ring is full, about a second of queries and positions, so the client polls every 0.125 s.
- **Invalid mailbox data.** Ring offsets must be inside the 2 KB buffers, and every packet must fit entirely in the published outgoing bytes and contain its five-byte protocol header. Invalid data restarts discovery without consuming packets or reporting checks. Parsing is bounded by the published byte count so a damaged mailbox cannot trap the client in a loop.

Boss completion is stored in Archipelago server data under `ootxmm_goals_<seed>_<team>_<slot>`. Each boss updates its own boolean in a dictionary; the client waits for `Retrieved` or `SetReply` to confirm the server stored it before acknowledging the pickup. A dropped socket therefore leaves the game's reliable boss packet pending. An update preserves the other boss. The client reloads the dictionary on login and merges delayed replies with newly seen bosses. Mailbox resets and game switches preserve the local result. Keep the server save to preserve this progress across server restarts. `test/test_client.py` covers the protocol, both boss orders across client restarts, game switches, reconnects and slot/seed isolation against a simulated mailbox.

`tools/client-smoke.py` runs a loopback WebSocket check against Archipelago with two simulated mailboxes. With Archipelago's Python, run `python tools/client-smoke.py --archipelago <test checkout> --seed <two-player .archipelago>`. Install the current world in that checkout first and use `goal: both` for both slots. It checks bidirectional check/item delivery, duplicate checks, replay after a dropped send, fresh clients, a temporary server disk-save reload, slot isolation and both boss orders. It never opens the group's server save. Real pickups, game switches and boss victories remain part of the gameplay checklist.

For command-driven emulator checks, `tools/bizhawk_boot.lua` creates a disposable file and waits for a moving mailbox, then writes a gameplay screenshot and state. Launch BizHawk with a separate `--config=<file>`, `--lua=<script>`, `--userdata=out:<absolute output directory>` and the matching ROM as the last argument. Keep save paths in the separate config under the test directory. `--gdi` and a hidden process window avoid interactive file dialogs; this still runs the emulator frontend and core.

## OoTMM build
The ROM patch and the in-game multiworld code come from OoTMM itself, built from source with our changes ([Our OoTMM changes](#our-ootmm-changes)). `pwsh tools/ootmm-build.ps1` builds it inside WSL (distribution `Ubuntu-24.04`, as root):
- `tools/ootmm-build.sh` keeps a checkout of the tracked release ([ROADMAP.md](ROADMAP.md#decisions)) in `/root/ootmm`, resets it to the tag on every run and applies `ootmm-patches/*.patch` (our changes, as `git diff` output against the tag), so the patches are the only changes. It copies the ROMs from `roms/`, which OoTMM's build reads, and our scripts from `ootmm-ap/`.
- The build runs in OoTMM's own toolchain image (`ghcr.io/ootmm/toolchain:1.4`, the one its CI uses) under Podman. Ubuntu's own MIPS compiler is too old for OoTMM's C code. The checkout is mounted at the same path inside the container, so CMake caches stay valid, and `/mnt` (the Windows drives) is mounted too.
- Extra arguments run a command in the checkout inside the image instead of the build. A test seed: `pwsh tools/ootmm-build.ps1 "cd packages/generator && NODE_ENV=production pnpm start --seed test"` writes the ROM, the `.ootmm` patch and the spoiler to `/root/ootmm/packages/generator/out` (`\wsl$\Ubuntu-24.04\root\ootmm\...` from Windows).
- WSL itself is set up once with `wsl --install -d Ubuntu-24.04` (needs admin and a reboot); the script installs Podman and pulls the image on first use.
- On macOS and Linux, `sh tools/ootmm-build-docker.sh` does the same with Docker. Its checkout lives in `$OOTMM_SRC` (default `~/.cache/ootmm-decrypted/ootmm`) and is mounted at the same path. `--seed <folder>` mounts a seed folder at `/seed` for `ap-patch.ts`. The image is x86-64 only, so Apple Silicon runs it under emulation; a fresh build and one patch took about five minutes on an Apple Silicon Mac.

### ROM patch
A player's ROM is built from their Archipelago output with OoTMM's generator:
1. `generate_output` in `world.py` writes `<seed>_P<n>_<name>.ootxmm.json` into the seed's output: OoTMM's seed string, the player's OoTMM settings (`ootmm_settings`), the exact price table and, for every check, the OoTMM item there and whether it is the player's own. Another player's item shows as itself if it is an OoTMM item, else as a stand-in for its classification (`FOREIGN_STAND_INS`: the Triforce for progression, a heart piece for useful, a green rupee otherwise).
2. `ootmm-ap/ap-patch.ts` (copied by `tools/ootmm-build.sh` to `packages/generator/lib/ap/`) runs OoTMM's logic with those settings up to its fill. Song events, entrances and starting items follow OoTMM. It replaces the prices with the exact Archipelago-generated table when present, then puts the seed's item at every check: the player's own items for world 1, others' items for world 2, a world that doesn't exist, so the game hands them to its multiworld code. It fails if the world and OoTMM disagree on which checks exist. The ROM is built in multiworld mode (`mode: multi`), so every pickup is reported.
3. Hints: OoTMM's hints come from its playthrough analysis, which can't run on one world of a multiworld. Gossip stones get junk hints; the fixed hints (where the dungeon rewards, the Light Arrows, the Oath to Order and Ganon's boss key are, and how important the items at the Skulltula House and similar checks are) are worked out from the placements as OoTMM does.
4. It embeds both compiled mailbox addresses in the reserved ROM header, then writes the ROM, OoTMM's `.ootmm` patch file and a private `.build.json` receipt binding the patch to its exact placement input. OoTMM's patch mode (`pnpm start --patch <file>`) rebuilds the same ROM from the patch file and the player's own ROMs, except for 32 random bytes OoTMM picks on every pack.

To run it: `pwsh tools/ootmm-build.ps1 "cd packages/generator && NODE_ENV=production pnpm exec tsx lib/ap/ap-patch.ts <player file or directory> ../../roms/oot.z64 ../../roms/mm.z64 <output folder>"`. Windows drives are mounted in the container, so the files can be `/mnt/c/...` paths. With the Docker script, pass `--seed <folder>` first and use `/seed/...` paths. A directory builds every `.ootxmm.json` file in name order and fails if none exist. A failed player stops the batch with a nonzero exit; outputs already built remain.

The host builds patches and distributes each player's `.ootmm`, not the ROM. Players apply it with OoTMM v33.0's Patch mode and their own ROMs; the patch carries our custom communication code. Both the standard v33.0 CLI and browser Patch modes rebuild these patches: the browser download matches the host-built ROM except for the 32 random player-ID bytes described above. See `docs/setup_en.md` for the player and host instructions.

### Our OoTMM changes
Each file in `ootmm-patches/` is one change, as a diff against the tracked tag. To change one: run the build once (the checkout then has every patch applied), edit `/root/ootmm`, and write the diff back with `git -C /root/ootmm diff v33.0` (add new files with `git add -N` first) into its patch file. Keep each one small and self-contained, so it can be offered upstream.

- `0001-ipc-ram-mailbox.patch`: OoTMM's multiworld code talks to the outside only through its IPC layer (`packages/generator/src/common/ipc/`), whose one backend drives the cartridge registers of OoTMM's own Project64 build. With multiplayer on and no connection, the second item sent waits forever for an ack (`Multi_EnsureSendBufferEmpty` in `src/common/multi/multi.c`), so the game locks. The patch adds a backend that is used when that Project64 isn't there (`src/common/ipc/ram.c`): a mailbox in RDRAM that a BizHawk client reads and writes. Its layout, all big-endian: magic `OoTMM-IPC-RAM-1` (16 bytes, 16-aligned, written last at init), `connected` (u32, the client sets it to 1 while attached), `alive` (u32, the game counts it up every frame: after a game switch the other game's mailbox may still be in RAM, and the live one is the one that moves), `outHead`, `outTail`, `inHead`, `inTail` (u32), then two 0x800-byte rings, game to client and client to game. Each ring holds packets as a big-endian u16 length then the packet; the writer moves the head, the reader the tail, and head equal to tail means empty. The packets are OoTMM's own (`src/common/multi/multi.h`). Every check the player gets is sent as a reliable WAL item packet with its check key, also when the item is the player's own, so the client learns every checked location from that one stream.

- `0002-remote-item-identity.patch`: remote pickups retain dungeon-specific item IDs in check overrides, even when the host uses own-dungeon placement. The host's dungeon context cannot identify another player's key or fairy; generic conversion can also produce an invalid OoT fairy ID. Generic conversion is disabled for remote items and their cloaks.

## Branches
- `main`: stable. Only moves to a commit `dev` already tested.
- `dev`: integration branch. Feature branches merge here first.
- `feature/<name>`: one feature or fix per branch. Delete it once merged; only `main` and `dev` stay.

## Syncing upstream
Upstream is `quasky` (Quasky/AP-OOTMM). Its branches are fetched into `refs/quasky/`, outside `refs/remotes/`, so Git clients don't list them as branches. Never merge it directly: import it with the sync script, which strips AI co-author trailers from commit messages deterministically, so repeated imports give the same hashes and later merges stay clean.

```
git remote add quasky https://github.com/Quasky/AP-OOTMM.git        # once
git config remote.quasky.fetch "+refs/heads/*:refs/quasky/*"        # once
pwsh tools/sync-upstream.ps1                                        # -> clean/quasky-main
git merge clean/quasky-main
```

The script needs `python -m pip install git-filter-repo`.

## Conventions
- Commit messages are plain and descriptive. No co-author trailers for tools, and no mention of AI assistants anywhere in commits, code or docs. Local assistant files (`CLAUDE.md`, `AGENTS.md`, `.claude/`) are listed in `.git/info/exclude` and never committed.
- The game name `OOTxMM` is what seeds and clients match on. Changing it is a breaking change.
- Update `ROADMAP.md` in the same commit that starts or finishes an item: add its row when work starts, delete it when the item is done. The roadmap and docs describe the current state, never history. At the end of a change, grep `ROADMAP.md` and the docs for its topic and remove anything it made stale.
- Credit ported work (`cherry-pick -x` or a source note) and keep the README's Credits current.
